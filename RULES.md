> **Как пользоваться.** Это правила игры вашего проекта. Файл лежит в корне репозитория под
> именем `RULES.md` — в стартовом проекте курса он уже там. Замените `<...>` на своё и закоммитьте. Этот блок
> не удаляйте: он объясняет каждому в команде, как с файлом жить.
>
> **`RULES.md` один на всю команду и лежит в git.** В сессиях агент читает ваш личный файл,
> `RULES.md` — исходник, из которого личный файл собран. Каждый участник **один раз** собирает
> личный файл из `RULES.md`:
> `CLAUDE.md` — для Claude Code, `AGENTS.md` — для остальных агентов. Если ваш клиент читает
> файл с другим именем, назовите личный файл так, как требует клиент. Скажите своему агенту:
> «Прочитай RULES.md и создай наш с тобой CLAUDE.md» (или `AGENTS.md`).
>
> **Личный файл в git не кладём**, его имя уже стоит в `.gitignore` — список ниже, в разделе
> про git. У каждого в команде своя зона и свой агент. Чужой личный файл в общем репозитории
> подсунул бы вашему агенту чужую роль.
>
> При сборке правила игры переносятся в личный файл **полностью**. Дальше дописывается
> личное: ваша зона в продукте, как вы с агентом общаетесь, лимиты вашего тарифа.
> Ослаблять правила игры в личном файле нельзя. Меняются они только здесь, по согласию
> команды. Поменялись — пересоберите свой файл: что изменилось, покажет `git log -p RULES.md`.
> ⛔ Не раздувайте личный файл: он уходит в каждый запрос и съедает контекст.

# Правила игры проекта

Проект учебный по происхождению. Правила в нём — боевые: так же пишут требования, так же
принимают работу и так же теряют данные. Поблажек на «это же учебное» здесь нет, потому что
в реальном проекте их тоже не будет.

Отвечать по-русски. Решения по коду принимай сам; на развилке — один вопрос с вариантом,
который считаешь лучшим.

## Команда

<Кто в команде и за какую часть продукта отвечает: имя — зона.>

Агент работает на компьютере одного человека и слушается только его. **Владелец** в правилах
ниже — тот, за чьим компьютером идёт работа. Чужую зону агент без просьбы её хозяина не трогает:
нужна правка там — сказать владельцу, он договорится с хозяином зоны.

## ⛔ Красные линии — никогда, даже если это «правильное решение»

Всё, что ты запускаешь, ты запускаешь на **личном компьютере человека**: там учёба, документы,
фотографии и живые пароли в браузере. Сломанное окружение — это не «переустановим за час».

| Никогда | Почему |
|---|---|
| `sudo` (macOS/Linux), PowerShell «от имени администратора» (Windows) | Меняет систему целиком и молча. Нужны права администратора — значит подход неверный: остановись, объясни, спроси |
| `rm -rf`, `rm` по маске `*`, `Remove-Item -Recurse -Force` вне папки проекта | Отменить нельзя, Корзины нет |
| `pip install` мимо венва, `sudo pip` | Ломает питон, которым пользуется сама система |
| `brew install python`, правка `/usr/bin/python3` | Системный питон принадлежит ОС. Его подмена ломает системные утилиты |
| Правка `PATH`, `~/.zshrc`, `~/.zprofile`, переменных среды Windows | Сломанный `PATH` = терминал перестаёт открываться |
| `curl … \| sh`, `iwr … \| iex` | Исполнение кода из интернета вслепую |
| `git push --force`, `git reset --hard`, `git clean -fd`, `git checkout -- .` | Тихо уничтожают несохранённую работу — свою и чужую |
| Запись вне папки проекта: Документы, Рабочий стол, Загрузки, iCloud, OneDrive | Чужие файлы. Мы к ним не прикасаемся |
| `chmod -R`, `chown`, `Set-ExecutionPolicy`, Keychain, диспетчер учётных данных | Права и пароли — не территория агента |
| Отправка наружу: публичный репозиторий, gist, вебхук, чужой API | Опубликованное не отзывается |

**Правило одной кнопки.** Команда что-то **удаляет**, **устанавливает** или **меняет настройки
системы** — сначала одной человеческой фразой: что она сделает и что будет, если не делать.
Потом спросить. Потом запускать.

## Где живёт проект

Всё — в одной папке проекта. Что создаёшь, читаешь и удаляешь — внутри неё. Временные файлы —
в `tmp/` **внутри проекта**, не в системном `/tmp` и не на Рабочем столе.

## Стек и структура

Проект собран из стартового проекта курса. Стек меняется только по согласию команды
и преподавателя.

| Часть | Технологии | Папка |
|---|---|---|
| Бэкенд | Python 3.13, FastAPI, SQLAlchemy 2, Alembic | `backend/` |
| База | PostgreSQL 16 | в Docker |
| Фронт | React 19, TypeScript, Vite | `frontend/` |
| Тесты бэкенда | pytest против тестовой базы, линтер ruff | `backend/tests/` |
| Тесты фронта | Vitest, Testing Library, MSW, ESLint, проверка типов | рядом с кодом, `*.test.tsx` |
| E2E | Playwright, настоящий браузер | `e2e/` |

**Всё работает в Docker.** На компьютере нужны Docker, git и IDE. Python, Node и браузер
для тестов на компьютер не ставим — они живут в контейнерах.

- Запуск: `docker compose up --build`. Фронт — http://127.0.0.1:5173, документация API —
  http://127.0.0.1:8000/api/docs
- Все адреса бэкенда начинаются с `/api`. Фронт пересылает туда запросы сам: адрес бэкенда
  в коде фронта не пишем.
- Библиотека для бэкенда: `docker compose run --rm backend uv add <пакет>`. Для фронта:
  `docker compose run --rm frontend npm install <пакет>`. Обе команды обновляют файл
  зависимостей и lock-файл, их коммитим. После смены зависимостей: `docker compose up --build -V`
  — без `-V` фронт стартует со старыми библиотеками из прошлого запуска.
- ⛔ `pip install`, `npm install -g`, системный `/usr/bin/python3` — никогда.

## База и миграции

- **Схема базы меняется только миграцией.** Порядок: модель в `backend/app/models/` →
  импорт в `backend/app/models/__init__.py` →
  `docker compose run --rm backend alembic revision --autogenerate -m "что сделали"` →
  прочитать файл в `backend/migrations/versions/` глазами → `docker compose up`, миграции
  накатятся сами.
- ⛔ Руками в базе схему не меняем, ни через DBeaver, ни SQL-запросом: у соседа по команде
  этой правки не будет.
- Бизнес-правила — в схеме: NOT NULL, UNIQUE, внешние ключи, CHECK. Правило, которого
  нет в схеме, база не держит.
- Тесты сторожат миграции: модель поменяли без миграции — красный
  `test_models_match_migrations`; откат миграции не работает — красный
  `test_downgrade_and_upgrade_again`.
- DBeaver: хост `127.0.0.1`, порт `5432`, база, логин и пароль — из `docker-compose.yml`
  или вашего `.env`.

## ⛔ Секреты — их ломают первыми

- Ключи и пароли — **только в `.env`**, и он в `.gitignore` с первого коммита.
- Рядом `.env.example` с пустыми значениями — его коммитим, он показывает состав переменных.
- ⛔ Ключ в коде, в README или в истории git — **утёк навсегда**. Удаление файла не помогает:
  он остаётся в истории. Утёк — идём в личный кабинет и отзываем.
- Секрет всё-таки попал в коммит — сразу и прямо сказать об этом команде.
- Перед коммитом проверить, что пусто:
  `git diff --cached | grep -iE "sk-|AIza|token|password|secret"`

## Тесты — граница между «написал» и «готово»

**Полный прогон** — три команды, все три должны быть зелёными:

```
docker compose -f docker-compose.test.yml run --rm --build backend-tests
docker compose -f docker-compose.test.yml run --rm --build frontend-tests
docker compose -f docker-compose.test.yml run --rm --build e2e
docker compose -f docker-compose.test.yml down -v
```

В прогон входят линтер и формат бэкенда, тесты бэкенда, линтер, проверка типов и сборка
фронта, тесты фронта и e2e в браузере. Тестовый стек отдельный: базы в памяти, рабочие
данные он не видит, приложение можно не останавливать.

- ⛔ **Слово «готово» — только после зелёного полного прогона, e2e включительно.** Итог —
  числом: «бэкенд 12 из 12, фронт 8 из 8, e2e 3 из 3».
- Каждая фича — тесты на каждом слое, который она задела: API-тест на успех и на отказ
  (404, пустой ввод, чужой id), тест компонента, e2e на сценарий пользователя.
- Новый тестовый файл — строка в `TESTS.md`.
- Красный тест не удаляем и не комментируем. Либо чиним код, либо осознанно правим тест
  и говорим об этом вслух.
- ⛔ Тесты не ходят в интернет и в боевые сервисы. На бэкенде внешние сервисы мокаем,
  на фронте сеть подменяет MSW.

## Комментарии — их читает следующая сессия

Агент забывает всё между сессиями. Код — единственная опора, которая остаётся.

- **Docstring модуля**: зачем этот файл и какую проблему решает. Не пересказ кода.
- **`AI:`-тег** на граблях и неочевидных решениях:
  `# AI: id пользователя берём из сессии, из формы им можно подменить чужой`.
  Один `grep -rn "AI:"` показывает все опасные места. ⛔ Тег на технической мелочи — шум:
  ставим там, где следующий человек может обжечься.
- По-русски, в плотности окружающего кода.
- Проверяется тестами: у модуля бэкенда нет docstring или у файла фронта нет
  шапки-комментария — прогон красный. Тег `AI:` машина не проверит, он на вашей совести.

## Docker

- ⛔ Порты публиковать **только на `127.0.0.1`**: `"127.0.0.1:8000:8000"`, не `"8000:8000"`.
  Иначе в университетском или публичном Wi-Fi ваша база открыта всей сети.
- `.dockerignore` лежит рядом с каждым Dockerfile. Без него в образ уезжают `node_modules`
  и `.venv` с вашего компьютера, собранные под другую систему, и сборка ломается.

## Mac и Windows в одной команде

Docker сглаживает разницу окружений, но три вещи ломают совместную работу:

- **Переводы строк.** Заведите `.gitattributes` с одной строкой `* text=auto eol=lf`.
  Иначе после коммита с Windows вся команда видит файл изменённым целиком, и в diff не
  разобрать, что реально поменялось. Shell-скрипт с CRLF в контейнере падает с
  `bad interpreter`.
- **Регистр в именах файлов.** macOS и Windows его не различают, Linux внутри контейнера —
  различает. `Index.html` в коде при файле `index.html` на диске: у автора работает,
  в Docker падает. Пишите имя ровно так, как файл лежит.
- **Команды из этого файла рассчитаны на bash.** На Windows запускайте их в **Git Bash**
  (ставится вместе с Git), не в PowerShell и не в cmd — `grep` там не работает.

Пути в коде — через `pathlib.Path`: при склейке строк со слэшами `\` и `/` разъезжаются.

## Первые задачи команды

Стартовый проект даёт каркас и тесты к нему. Остальное команда делает сама, по этим
правилам и с гейтом на каждую задачу:

1. **Имя проекта** в `docker-compose.yml`: `name: app` → короткое латинское имя продукта.
2. **`.gitattributes`** — раздел «Mac и Windows в одной команде».
3. **`.env.example`** — все переменные из `docker-compose.yml` без значений.
4. **Скрипт полного прогона:** одна команда запускает три прогона подряд, останавливается
   на первом красном, печатает итог числом и гасит тестовый стек.
5. **Первая сущность целиком:** модель → миграция → API → экран → тесты на каждом слое.
   По ней агент будет делать все следующие.

## Как работаем

- **План до кода.** Сначала списком: что делаем, какие файлы трогаем, как проверим. Потом код.
- **Одна задача — одна сессия.** Закрыл фичу — начинай новую, контекст не копим.
- **Перед рискованной правкой — коммит.** Это единственная точка возврата.
- ⛔ **Не чинить каскадом.** Стало хуже после твоей правки — остановись, вернись к коммиту
  и покажи, что именно произошло. Пять команд подряд «на авось» — так теряют проект.
- ⛔ **Скоуп не расширяется.** Просили страницу регистрации — делаешь её. Смежное предлагаешь
  строкой, молча не делаешь.
- ⛔ **«Написал» ≠ «проверил».** Итог — числом: «3 из 3 тестов зелёные».
- После задачи короткий отчёт: что сделано, какие файлы, что осталось.

## Когда что-то пошло не так

1. Остановиться. Не запускать следующую команду наудачу.
2. Показать текст ошибки целиком и перевести на человеческий.
3. Предложить **один** следующий шаг.
4. ⛔ Никогда не лечить ошибку правами. Администраторский запуск в ответ на `permission denied`
   превращает мелкий сбой в сломанную систему.

## Git: команда в одном репозитории

- **Перед началом работы — `git pull`.** Всегда, даже если вчера всё забирал.
- **Своя задача — своя ветка.** В `main` вливается только принятое по гейту.
- **Закончил кусок — коммит с подписью по сути и push.** День без push означает день работы,
  которого у команды нет.
- **Конфликт разбирает человек.** Агент показывает обе версии и ждёт решения владельца.
  ⛔ Молча оставить свою версию поверх чужой — нельзя.
- Репозиторий **приватный** по умолчанию: в учебном проекте всегда оказываются личные данные —
  ФИО, оценки, переписка, тестовые пользователи.
- ⛔ Коммит и пуш — по просьбе владельца. Но предлагать коммит после каждого законченного куска.
- `.gitignore` лежит в стартовом проекте: зависимости, сборки, отчёты тестов, `.env`,
  личные файлы агента `CLAUDE.md` и `AGENTS.md`, мусор macOS и Windows. Новое служебное —
  дописываем туда же. Перед коммитом `git status` не показывает ни `node_modules`, ни `.env`.
- Рудименты генераторов (`main.py` с «Hello from...») — удалять сразу.
- README: что за проект, как запустить, как прогнать тесты. Пустым README не оставляем.
- Коммит по-русски и по сути: «добавлена миграция таблицы пользователей», не «fix» и не «update».
